<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| anon role → app_config | Anon can SELECT all rows; no INSERT/UPDATE/DELETE policy |
| service_role → app_config | service_role bypasses RLS and can UPDATE thresholds via Studio |
| supabase CLI → remote project | CLI uses service_role credentials from linked project; runs in controlled environment |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-01 | Tampering | app_config RLS | mitigate | No INSERT/UPDATE/DELETE policy for authenticated role; only service_role can modify thresholds. Verified via supabase db lint --linked. |
| T-01-02 | Elevation of Privilege | app_config anon SELECT | accept | Thresholds are non-sensitive tuning parameters (GPS radius, accuracy floor). Anon read is intentional per CONTEXT.md D-01 — client uses verify_radius_m for "get closer" UX feedback. |
| T-01-03 | Information Disclosure | database.types.ts committed to git | accept | Generated types expose schema shape (table/column names) — this is intentional, standard practice for typed Supabase clients. No PII or secrets in type definitions. |
| T-01-04 | Tampering | Migration schema drift via Studio SQL editor | mitigate | CONTEXT.md D-02 explicitly forbids Studio SQL editor changes. Migration files are source of truth. Enforced as team rule; verify with supabase db diff if drift suspected. |
| T-01-SC | Tampering | npm/pip/cargo installs | accept | No new packages installed in Plan 01-01 (supabase CLI already installed at 2.100.1). Package legitimacy audit in RESEARCH.md covers all installed packages. |
</threat_model>
