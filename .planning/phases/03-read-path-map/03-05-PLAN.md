<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| filter chips → bbox RPC | Filter flags become RPC params; the server applies them. The client must not use filters to hide moderation-excluded rows (those are already gone server-side). |
| denied-GPS manual search → map | User-entered viewport drives the bbox query; no external geocoding API is contacted in Phase 3. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-19 | Tampering | filter params | mitigate | Filters are additive `(not filter or cond)` clauses in the RPC; they can only narrow, never reveal moderation-excluded rows. Client cannot widen past the server filter. |
| T-03-20 | Information Disclosure | denied-GPS search | mitigate | No external geocoding provider / API key introduced (OQ-4); manual search only recenters the map + re-queries the bbox RPC, so no third-party data egress. |
| T-03-21 | Information Disclosure | empty-state copy / logs | mitigate | Empty/denied states show generic copy; no coords, address, or filter payload logged (CLAUDE.md no-PII). |
| T-03-SC | Tampering | package installs | mitigate | No new installs in this plan (expo-location already present from Phase 1). |
</threat_model>
