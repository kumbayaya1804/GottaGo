**File:** `01.5-02-PLAN.md`, frontmatter (lines 3–4)

**Issue:** `wave: 1` conflicts with `depends_on: ["01.5-01"]`. A plan cannot be wave 1 AND depend on another wave 1 plan. If the executor processes wave 1 plans as a parallel batch, plan 02 could start before plan 01 completes — before `docs/design/flows.md` and `docs/design/wireframes.md` exist. **Fix:** Change `wave: 1` to `wave: 2` in `01.5-02-PLAN.md` frontmatter.

```yaml

depends_on:
  - "01.5-01"

# After
wave: 2
depends_on:
  - "01.5-01"
```

### RC-02 — "Duplicate Location" report type not in live DB CHECK constraint

**Files:** `01.5-01-PLAN.md` (Flow 12, Task 1 lines ~134–135; Wireframe 19, Task 2 line ~249)

**Issue:** The report flow specifies 5 user-visible options: Permanently Closed, Access Denied / Currently Locked, Code is Wrong, Dirty or Unsafe, **Duplicate Location**. The first four map to valid `reports.report_type` values in the live schema CHECK constraint:

```sql
check (report_type = any(array[
  'permanently_closed','moved_relocated','currently_locked',
  'now_requires_purchase','staff_pushed_back','access_tightened',
  'dirty_unsafe','changing_station_unusable','inaccurate_information'
]))
```

`'duplicate_location'` is **not** in this array. Phase 7's `report_location` RPC cannot store a "Duplicate Location" report without a migration first. If implemented without this note, Phase 7 would hit a DB constraint violation in production.

**Fix:** Add a schema dependency note to the Report Flow section in Plan 01 (after the Flow 12 task):

```
Schema dependency: "Duplicate Location" requires adding 'duplicate_location'
to the reports.report_type CHECK constraint via Phase 7 migration before
the report_location RPC is implemented.
```

Also clarify the full mapping in the plan (CONTEXT.md documents "Code is Wrong" → `inaccurate_information` but is silent on "Duplicate Location"):

| User Label | DB value |
|---|---|
| Permanently Closed | permanently_closed |
| Access Denied / Currently Locked | currently_locked |
| Code is Wrong | inaccurate_information |
| Dirty or Unsafe | dirty_unsafe |
| Duplicate Location | duplicate_location (requires migration in Phase 7) |

### RC-03 — `has_changing_table` source is tags table, not a locations column

**Files:** `01.5-01-PLAN.md` (Rating Screen wireframe #21, Flow 13); `01.5-02-PLAN.md` (Section 13, Section 8)

**Issue:** Both plans use `has_changing_table === true` as if it's a field on the location object. The live `locations` table has no `has_changing_table` boolean column. This information is stored in the `tags` table as a key-value pair: `{ key: 'has_changing_table', value: 'true' }`.

Phase 8's rating screen implementation needs to know how to derive this boolean. If Phase 8 checks `location.has_changing_table`, it will always get `undefined` (the field doesn't exist).

**Fix:** Add a derivation note to Rating Screen wireframe (Plan 01) and Section 13 of Plan 02:

```
has_changing_table is derived from the tags table:
  tags.find(t => t.key === 'has_changing_table')?.value === 'true'
Phase 3 search_locations_bbox RPC must include tags in the location
response payload, OR Phase 8 must perform a separate tags lookup.
```

The Submit Flow Step 1 (wireframe #12) shows "Baby Changing Table" as a checkbox — the implementing plan must also clarify that submitting this flag writes a row to the `tags` table (not a locations column).
