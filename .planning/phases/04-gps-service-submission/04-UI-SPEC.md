# Phase 4 — UI Design Contract

> Visual and interaction contract for the GPS Service & Submission phase. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Scope of this contract:** the 3-step SubmitFlow wizard (`app/src/app/(tabs)/submit.tsx`), the `access_sensitivity` toggle, the conditional PIN field, the "Update door code" action on the existing `LocationDetailSheet.tsx`, and the new submitter-only pending-status sheet with a "withdraw submission" action.
>
> **This is not a greenfield design.** Gotta Go has a shipped, mandatory design system at `docs/design/design-system.md` (source of truth for Phase 2–8) with committed token constant files. This contract does not re-invent tokens — it names the exact existing tokens each new Phase 4 surface must use, and locks the phase-specific copy. Every screen must also pass the **Component Acceptance Checklist (design-system.md §20)**, cited in each PLAN.md per ROADMAP SC10.

## Spacing Scale

Declared from the committed `spacing.ts` (design-system.md §3). Screens this phase builds use these tokens:

| Token | Value | Usage in Phase 4 |
|-------|-------|------------------|
| xs | 4px | Icon-to-label micro gaps (progress dots, toggle icon), inline padding |
| sm | 8px | Checkbox/segment internal padding, gap between explainer icon and text |
| md | 12px | Between stacked form fields, between list items |
| base | 16px | Standard horizontal screen margin, form card padding, input padding |
| lg | 20px | Between a form section (e.g. Policy) and the next section (Accessibility) |
| xl | 24px | Between major wizard blocks, sheet bottom safe-area inset |
| xxl | 32px | Between major screen sections (Success screen icon → headline → CTA) |
| xxxl | 48px | Full-screen modal / Success screen top padding |
| giant | 64px | (not used in Phase 4 — FAB dimension only) |

**Exceptions / standing note:** The scale includes **12px (`md`)** and **20px (`lg`)**, which are not strict multiples of 8. This is an **accepted, documented standing exception** (03-CONTEXT.md **D-33**) — the token system shipped in Phase 1.5/2/3 and is an established structural fact. Do NOT flag `md=12` / `lg=20` as a spacing violation; they are the contract. All other values (4/8/16/24/32/48/64) are 4-point-grid aligned. Touch targets: standard interactive ≥44pt; the "I'm at This Location" / primary wizard CTA is 56pt height (design-system.md §6/§18.2).

## Typography

Declared from the committed `typography.ts` (design-system.md §2). Roles used by this phase's screens:

| Role | Size | Weight | Line Height | Usage in Phase 4 |
|------|------|--------|-------------|------------------|
| h2 | 22pt | SemiBold (600) | 28pt | Step / screen titles ("Add a Bathroom", "Access & Hours", "GPS Confirm"), Success headline "Location Submitted!" |
| h3 | 17pt | SemiBold (600) | 22pt | Form section headers ("Policy:", "Accessibility:", "Hours:"), pending-sheet name |
| body | 17pt | Regular (400) | 24pt | Input text, toggle label "Not suitable for kids", pending-sheet body copy, ghost/Back button labels |
| bodyMedium | 17pt | Medium (500) | 24pt | Primary button labels ("Next →", "I'm at This Location", "Back to Map", "Update door code"), distance |
| subhead | 15pt | Regular (400) | 20pt | Explainer microcopy under the sensitivity toggle, PIN helper "…only shown to signed-in users", hours/metadata, GPS accuracy readout |
| caption | 13pt | Regular (400) | 18pt | Progress-step labels, `< Pending >` badge text, timestamps, inline error text |

**Exceptions / standing note:** The project's full scale is **5 sizes across the phase's screens (34/28/22/17/15/13/11 available) and 3 weights (400/500/600/700)** — this exceeds the generic UI-SPEC "3–4 sizes, 2 weights" guideline. This is an **accepted, documented standing exception** (03-CONTEXT.md **D-33**) — the token system is already shipped and is the design contract for Phases 2–8. Do NOT flag the size/weight count as a violation. Phase 4 introduces **no new** typographic values; it only consumes the existing scale. Dynamic Type: layouts must survive ±5 accessibility steps; `numberOfLines` is forbidden on critical labels (name, distance, CTA text, error copy) — design-system.md §18.5.

## Color

The generic 60/30/10 model mapped onto this app's shipped light/dark token system (design-system.md §1). Values shown light / dark.

| Role | Value (light / dark) | Token | Usage |
|------|----------------------|-------|-------|
| Dominant (~60%) | #FFFFFF / #121212 | `background` | App/form background, wizard scroll surface, Success screen |
| Secondary (~30%) | #F8F9FA / #1E1E1E | `surface` | Bottom sheet (pending-status sheet), input-field grouping, card/modal backgrounds |
| Accent (~10%) | #1A73E8 / #8AB4F8 | `primary` | Reserved list below — never "all interactive elements" |
| Destructive | #D93025 / #F28B82 | `emergency` | The **"Withdraw submission"** action only (Level 3 destructive button) |

**Accent (`primary`) reserved for — explicit list for this phase:**
- Primary/filled CTA buttons: "Next →", "I'm at This Location", "Back to Map", "Update door code", and the confirm button inside the sensitivity dialog
- Active progress-step indicator in `①────○────○` (done/active dots use `primary`; upcoming dots use `border`/`textDisabled`)
- Selected `policy_tag` segment in the segmented picker (Step 1)
- The `access_sensitivity` switch ON-state track tint (D-13 — a switch/toggle, visually distinct from the policy segmented picker)
- The "No address? Describe the location instead" text affordance and any inline text links (D-04)

**Reserved for semantic tokens (NOT accent, do not substitute `primary`):**
- GPS accuracy "good" readout → `successGreen` + `checkmark-circle`; "poor" → `warningAmber` + `warning-outline` (design-system.md §18.4)
- Inline submit/GPS error text → `errorRed` + `alert-circle` (ERR-02/03/08)
- Pending pin + `< Pending >` badge → `pinPending` (#9AA0A6 light / #5F6368 dark), dashed-outline treatment, with the literal text "Pending" (never color-only)
- `code_required` policy badge → `emergencyOrange`/`pinCodeRequired` pill with **`textPrimary`** text (white fails contrast on amber — design-system.md §1.3/§8)

Every status indicator pairs color with an icon **and** text (WCAG 1.4.1, design-system.md §18.4). The `access_sensitivity` toggle state is conveyed by the switch position + label, not color alone.

### Error states (LOCKED — design-system.md §15; handle all applicable)

| State | Trigger | Exact copy | Treatment |
|-------|---------|-----------|-----------|
| ERR-08 Failed Submit | `submit_location` RPC error | `Couldn't submit your location. Check your connection and try again.` | Inline below Submit; `alert-circle` `errorRed`; `Retry` secondary button; form data preserved |
| ERR-02 GPS Low Accuracy | accuracy > 50m on Step 3 | `GPS accuracy too low — move to an open area and try again.` | Inline below GPS readout; `warning-outline` `warningAmber`; "I'm at This Location" disabled; re-enables live as accuracy improves |
| ERR-03 GPS Stale Fix | fix timestamp stale (>60s) | `GPS fix is stale — wait a moment and retry.` | Inline; `time-outline`; button disabled; `Retry` requests fresh read |
| ERR-01 GPS Denied | OS permission denied at Step 3 | `We can't find your location. Use search to browse bathrooms near an address.` | Inline; no blocking modal; no dead end |
| ERR-10 Auth Required | (guard) whole SubmitFlow requires sign-in from the start (D-18) | `Sign in to contribute` | Inline slide-up `AuthRequiredModal` — NOT a hard redirect; returns to Submit after auth |

> The RPC returns a **generic** GPS-rejection error (SC7); the client maps it to the friendly copy above — it must NOT surface the specific reason (mock/accuracy/freshness) beyond the mapped message.

## Registry Safety

| Registry | Blocks Used | Safety Gate |
|----------|-------------|-------------|
| shadcn official | none | not applicable — React Native project, no shadcn/registry in use |
| third-party registries | none | not applicable |

No component-registry dependency exists in this stack. The only potential net-new package this phase is a **Google Places autocomplete** provider for the D-04 address affordance — and RESEARCH **OQ-1** recommends deferring live autocomplete (coordinates come from GPS per D-05, so autocomplete is pure UX sugar). Default: ship the free-text + "Describe the location instead" toggle **without** live autocomplete. If the user later puts Places autocomplete in scope, the planner MUST gate any package behind a `checkpoint:human-verify` (slopcheck + `npm view`) before install — this is the equivalent of the registry vetting gate for this stack.
