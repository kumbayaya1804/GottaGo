<objective>
Build the published-location access-code UPDATE path (D-21/D-22/D-24/D-25). Add code-freshness and pending-code columns to `locations`, and create three authed-only RPCs: `update_access_code` (stages a proposed code without overwriting), `confirm_access_code` (a second, different authed user confirms → the stage-then-confirm gate that resolves RESEARCH OQ-3), and `get_access_code` (authed-only read for the "Update door code" UI, never widening the public detail RPC — RESEARCH Pitfall 4).

Purpose: Implements the "submit/update the access code" requirement fully in Phase 4, with the same abuse-resistance model that gates location publishing, so a single malicious update cannot silently break a working door code for everyone.
Output: One migration, one pgTAP suite, regenerated `database.types.ts`, live-pushed schema.

Decision (resolves OQ-3): the D-24 "1 confirming verification" is modeled as a **stage-then-confirm** pair on `locations` (`pending_access_code`, `pending_code_proposed_by`) that requires a second, distinct authenticated user to confirm before the code goes live. This mirrors the publish-confirmation pattern and is the minimal abuse-resistant mechanism (RESEARCH §Pattern 5 recommendation).
</objective>

## STRIDE Threat Register
| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-07 | Tampering / DoS | malicious code overwrite | mitigate | Stage-then-confirm: update_access_code only stages; confirm_access_code requires a DIFFERENT authed user to promote (D-24). |
| T-04-08 | Information Disclosure | access code exposure | mitigate | Code lives only in locations.access_instructions / pending_access_code; public search never selects it; get_access_code is authed-only; get_location_detail unchanged (Pitfall 4, SC6). |
| T-04-09 | Elevation of Privilege | grant drift on code RPCs | mitigate | revoke public + anon, grant authenticated, exact signatures. |
| T-04-10 | Repudiation | no code history (D-25) | accept | Deliberate: correctable fields carry no audit trail anywhere in this schema; disputes route through the Report flow (D-11, Phase 7 gap D-16 tracked). |
