# Phase 5 — UI Design Contract

> Visual and interaction contract for the Phase 5 trust-engine/verification client surfaces. Generated by gsd-ui-researcher, verified by gsd-ui-checker. This contract REUSES the standing Phase 1.5 design system (`docs/design/design-system.md`) — it does not redesign it. All tokens below are references into that source of truth, not new declarations.

**Scope — three client surfaces (plans 05-03 and 05-04):**

1. **VerifyFlow + candidate discovery** — a second user discovers nearby pending submissions (500m fixed radius, D-35/37) and submits a GPS verification. Handles `accepted / rejected / denied-permission / loading` states with a SINGLE generic rejection (mock-location and low-accuracy rejections are visually indistinguishable, per the standing ERR-09 security rule).
2. **Pending-submission progress indicator** (D-61) — creator sees "N of 2 verifications received" on their own pending submission, resolving in-app to a "Published!" state (D-68 fallback). No verifier identity or location exposed.
3. **Personal impact stat** (D-65) — private, non-comparative Profile stat, "You've helped verify N bathrooms". No rankings, badges, or leaderboards.

**Standing exception (do NOT re-flag):** Phase 1.5 established 5 typography sizes / 3 weights and 12px/20px spacing tokens as an APPROVED exception to the checker's generic 3-4 size / 2 weight and 8-point thresholds (project decision D-33). This phase reuses them unchanged. The checker must treat the design-system.md scale as the authority, not the generic template defaults.

## Copywriting Contract

Copy marked **[LOCKED]** is verbatim and must not be paraphrased (matches design-system §15 error matrix, existing `PendingStatusSheet`, and wireframes #16–18). Copy marked **[NEW — proposed]** is drafted here for planner/executor review; only the dynamic count/name varies.

### VerifyFlow (candidate discovery + verify)

| Element | Copy |
|---------|------|
| Primary CTA | **[LOCKED]** "I'm Here" (full-width, 56pt, `primary`; enabled only when client advisory pre-check passes: accuracy ≤50m AND within 100m) |
| Modal title | **[LOCKED]** "Verify Location" |
| GPS readout (good) | **[LOCKED pattern]** "Accuracy: {N}m ✓" + "You are {N}m away" (`successGreen`, `checkmark-circle`) |
| GPS readout (poor) | **[LOCKED]** "GPS accuracy too low — move to an open area and try again." (ERR-02; `warningAmber`, `warning-outline`; button disabled) |
| Discovery list heading | **[NEW — proposed]** "Verify a bathroom nearby" |
| Discovery empty state — heading | **[NEW — proposed]** "Nothing to verify nearby" |
| Discovery empty state — body | **[NEW — proposed]** "There are no pending bathrooms within walking distance right now. When you're near a newly submitted spot, it'll show up here to verify." |
| Success state | **[LOCKED]** heading "Verified!" + body "Thanks for keeping data fresh." (checkmark; reduced-motion → static) |
| Success dismiss | **[LOCKED]** "Done" |

### Error / rejection states (security-critical)

| Element | Copy |
|---------|------|
| Server rejection (ANY reason) | **[LOCKED]** "Unable to verify your location. Please try again." (ERR-09). **Every** server-returned rejection — mock-location (D-45), accuracy-floor (D-46), too-far, shadowban (D-38), cooldown (D-36), generic network — maps to THIS single string. The client MUST NOT branch copy on the RPC error; mock-location and low-accuracy rejections are visually identical. Recovery: "Try Again" re-reads GPS + retries. |
| Permission denied | **[NEW — proposed]** "Location access is off. Turn on location so we can confirm you're here." (denied sentinel `{denied:true}` → renders this state, never a dead end; offers a settings/dismiss affordance, not a blank screen) |
| Loading | Spinner permitted here (point-in-time action per §19); GPS-capture + RPC in flight. No skeleton (skeleton is for content areas). |

> **Client vs. server distinction (do not conflate):** the live accuracy/distance readout and the disabled-button pre-check are a client-side advisory UX (they never call the server, so showing "accuracy too low" there leaks nothing). Once `verify_location` is called, ANY rejection it returns collapses to the single generic ERR-09 string. This is the crux of SC7 — see design-system §15 ERR-09 note.

| Element | Copy |
|---------|------|
| Progress body | **[LOCKED]** "Pending — {N} of 2 GPS verifications received. Share with friends to speed up verification." (only `{N}` is dynamic; matches live `PendingStatusSheet.progressCopy`) |
| Pending badge | **[LOCKED]** "Pending" (`< Pending >` pill, `pinPending`, dashed, `clock-outline`) |
| Published resolution — heading | **[NEW — proposed]** "Published!" (`successGreen` accent + `checkmark-circle`) |
| Published resolution — body | **[NEW — proposed]** "Your bathroom is now live on the map. Thanks for helping people find a place to go." (this is the D-68 in-app fallback that appears on next view regardless of push; push is enhancement, never the only channel) |

### Personal impact stat (Profile, D-65)

| Element | Copy |
|---------|------|
| Stat sentence | **[NEW — proposed]** "You've helped verify {N} bathrooms." (`{N}` from `users.gps_verified_contribution_count`; singular "1 bathroom" when N=1) |

| Constraint | Private, non-comparative. NO rank, percentile, badge, leaderboard, streak, or "more than X% of users" framing. Sits alongside existing Profile stats (GPS Verifications / Locations Submitted / Ratings Given) as a plain count sentence, not a competitive metric. |

| Element | Copy |
|---------|------|
| Withdraw submission | **[LOCKED CTA]** "Withdraw submission" (`emergency`, destructive Level 3). ## Interaction & State Contract

The executor implements these states verbatim (SC7). No state may be a dead end (§17.2).

### VerifyFlow state machine

| State | Trigger | UI |
|-------|---------|-----|
| `loading` | Modal open / "Try Again" tapped | Live GPS acquiring; "I'm Here" disabled; spinner or live readout |
| `ready` | accuracy ≤50m AND within 100m (client advisory) | "I'm Here" enabled (`primary`, 56pt); live readout `successGreen` |
| `blocked` (advisory) | accuracy >50m OR too far | "I'm Here" disabled; ERR-02 / distance guidance inline (client-side, NOT a server leak) |
| `submitting` | "I'm Here" tapped | Spinner on button; RPC in flight |
| `accepted` | RPC success | Success state ("Verified! / Thanks for keeping data fresh." / "Done") |
| `rejected` | RPC error (ANY reason) | Generic ERR-09 inline; "Try Again" re-reads GPS. **Never reveals which check failed.** |
| `denied` | permission `{denied:true}` sentinel | Denied-permission copy + enable/dismiss affordance; not a dead end |

### Progress-indicator resolution

Pending sheet renders progress copy while `status='pending'`; on the creator's next view after the 2nd verifier publishes (`status='published'`), it resolves in-app to the "Published!" state (D-68). This resolution is independent of push delivery.
