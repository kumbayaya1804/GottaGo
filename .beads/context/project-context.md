- **dblink loopback source-address rewrite — the actual fix, root-caused with real Docker access (2026-08-01):** any dblink connection dialed to a loopback destination (`hostaddr=127.0.0.x`) gets its SOURCE address rewritten to `127.0.0.1` by the kernel regardless of which specific address was dialed — confirmed via `docker exec` (`inet_client_addr()` reports `127.0.0.1` even when `hostaddr=127.0.0.2` was used), so it always matches `pg_hba.conf`'s `127.0.0.1/32 trust` rule, which doesn't consume the supplied password and fails dblink's non-superuser password-auth check. The fix: dial the session's own real, non-loopback interface address, discovered dynamically at runtime via `host(inet_server_addr())` on the CURRENT connection (confirmed to return the real bridge IP both via direct `docker exec` and via the actual `supabase test db` invocation path — never assume a specific IP, always derive it live). No hardcoded address, no elevated role needed. See `supabase/tests/phase5_discovery_cooldown_race.test.sql` and `phase5_verify_publish.test.sql`.
- **pgTAP `plan()` must be called BEFORE `begin`, not inside it, in any file that later does a mid-script `rollback`:** verified empirically — `plan()`'s internal state is not purely sequence-based (the running per-test counter IS sequence-backed and survives rollback, but the declared plan total is not), so calling `plan()` inside a transaction that later rolls back silently breaks the very next assertion after the rollback with "You tried to run a test without a plan!" Root-caused via a minimal repro before fixing, not assumed. Relevant for any suite that mixes a rollback-cleaned single-session section with a later committed (dblink-requiring) section — see `phase5_verify_publish.test.sql`'s structure.
- **A submission's automatic `creator_claim` verification_events row (added by 05-02's `submit_location` rewrite) breaks any EARLIER logic that used "does this submission have any verification_events row" as a proxy for "has a real verifier looked at this" (2026-08-01, real regression, caught only by first-ever pgTAP execution):** `withdraw_submission`'s live D-58 cancel-vs-hard-delete check was written before `creator_claim` existed and needed a `event_type = 'verification'` filter added, plus (second-order bug) the hard-delete branch then needs to explicitly purge the submission's own `verification_events` rows first, since `verification_events.submission_id` has no `ON DELETE CASCADE`. General rule: when adding an unconditional event/audit row to an existing entity, grep every EXISTING query elsewhere in the codebase that does an unfiltered `exists(select 1 from <that table> where <fk> = ...)` — it may have assumed "any row" meant something narrower than what will now always be true.
- **Node `spawnSync` calls with no `timeout` option can hang a script forever if the child process hangs — a `finally` block cannot save you, because the synchronous call that's blocking never returns control to JS at all (2026-08-01, real, hit live in review):** fixed in `supabase/scripts/run-isolated-db-suite.js` by adding per-phase configurable timeouts (`RUN_ISOLATED_{START,TEST,STOP}_TIMEOUT_MS` env vars) plus best-effort process-tree kill on timeout (`taskkill /T /F /PID` on Windows, `pkill -9 -P` on POSIX — `spawnSync`'s own `killSignal` only kills the DIRECT child, not descendants like `docker.exe` spawned by `supabase.exe`). Validated for real: a genuinely wedged Docker Desktop daemon caused `supabase start` to hang, and the new 900000ms timeout correctly fired and let the script continue instead of hanging indefinitely.
- **An executable binding check beats a "keep these two files in sync" comment:** when a test must duplicate a migration's SQL statement to actually exercise logic the migration itself doesn't expose a hook for (e.g. `phase5_confidence.test.sql`'s backfill-mapping test), don't rely on a comment — use matching marker comments (`-- FOO-BEGIN` / `-- FOO-END`) in both files and a small Node test (`supabase/scripts/verify-confidence-backfill-binding.test.js`) that extracts and byte-compares them, failing loudly on drift. Mutation-test it (deliberately corrupt one copy, confirm the check fails, restore) before trusting it.

- **PL/pgSQL RETURNS TABLE gotcha (new, 2026-07-30 — caused a real 26-day live bug):** every column in a function's `returns table (...)` clause becomes an implicit body-scoped variable. An unqualified column reference elsewhere in the body that happens to share a name with an output column (e.g. `id`) is ambiguous under Postgres's default `plpgsql.variable_conflict = error`, and raises AT RUNTIME (on the specific call path that reaches the ambiguous statement), not at CREATE time — so it can ship silently and only fail for certain callers. Always alias-qualify table references inside a function whose RETURNS TABLE column names might collide (e.g. `from public.users u where u.id = ...`, not bare `where id = ...`).
- **PostGIS must be schema-qualified at the bootstrap `create extension` statement, not just at point of use (new, 2026-07-30):** `create extension postgis;` with no `with schema extensions` installs into the search_path default on a genuinely fresh database — breaking every later `extensions.geography`/`extensions.geometry` reference. Live was never exposed to this because Supabase's hosted platform auto-provisions PostGIS into `extensions` before user migrations run; only a from-scratch replay (local Docker/CI) hits it. Fixed 2026-07-30.
- **dblink from a non-superuser pgTAP session needs more than a password (new, 2026-07-30, unresolved):** `dblink_connect()` requires non-superuser callers to supply a password, but a bare connection string (no host) opens a Unix socket that Supabase's image authenticates via `peer` (ignoring the password); an explicit loopback IP like `hostaddr=127.0.0.2` doesn't help either, since `pg_hba.conf` matches the CLIENT's source address, and Linux's loopback routing still uses `127.0.0.1` as source regardless of destination. No working fix found yet — see `.planning/STATE.md` 2026-07-30 entries and `.beads/context/execution-state.md` before attempting either already-tried approach again.
- **SECURITY: never paste a live database password (or any credential) into assistant chat — even to ask for help running a command.** Happened 2026-07-30; treated as compromised and rotated immediately. If a command needs a password, ask the user to run it themselves in their own terminal rather than requesting the value.
- ColorScheme: ALWAYS use `useColorScheme() === 'dark' ? 'dark' : 'light'` (NOT `?? 'light'` — causes TS7053)
- expo-router typed routes: use `as never` cast for routes not yet in generated types
- PASSWORD_RECOVERY: handled via separate onAuthStateChange subscription in _layout.tsx (NOT in SessionProvider)
- `redirect.ts`'s `nextRoute` only auto-redirects authenticated users out of the literal `(auth)` route **group** (`segments[0] === '(auth)'`) — routes outside `(auth)`/`(tabs)` (e.g. `auth/callback`, `gps-consent`, `reset-password`) must navigate explicitly; the guard won't do it for them.
- Any screen where a session can appear mid-flow (before the screen is done with its own async work) must use the `suppressGuardRedirect` context field to prevent the root guard from racing it — see Established Patterns below.
- **D-08 null-include on filters (new, Phase 3):** any data-dependent filter clause on a nullable column MUST use an escape branch (`is not false`, `is null or =`, "no data at all" EXISTS check) — never bare equality. Bare equality on a nullable column silently excludes null rows, which is exactly backwards from this project's D-08 policy. A real bug (CR-02) shipped this way and wasn't caught until a manual code review.
- **NEVER embed a live Supabase access token literally in any command (new, Phase 3):** source it from a git-ignored file outside the repo (`~/.supabase-gsd-token`) via `source ~/.supabase-gsd-token && supabase ...` — the harness's credential-leakage classifier blocks literal tokens in commands, and rightly so.
- **Live database pushes need fresh explicit authorization every time (new, Phase 3):** even an obviously-correct fix authored autonomously during execution needs the user's specific go-ahead before `supabase db push` — general "you're executing this phase" authorization does not cover it.

## Established Patterns
- Supabase client: `import { supabase } from '@/lib/supabase'` (never recreate)
- Test mocks: jest.isolateModules + env save/restore (see app/src/lib/__tests__/supabase.test.ts)
- RPC style: SECURITY DEFINER set search_path = public + `revoke from public; revoke from anon; grant to authenticated` (both revokes required — Supabase auto-grants anon via ALTER DEFAULT PRIVILEGES)
- Migration header: phase comment block + `-- ─── N. Title ──` dividers + CONTEXT §ref + Pitfall refs
- Migration filename convention: draft a timestamp, but **rename to match what Supabase's `apply_migration` actually records live** after applying (its own timestamp, not the draft one)
- Screen convention: thin screens (logic in features/**); pure stubs via Bash to avoid TDD Guard
- Colors: `const colorScheme = useColorScheme() === 'dark' ? 'dark' : 'light'` (ternary, not nullish)
- Expo Router: `router.push('/(auth)/route' as never)` for routes not yet in generated types
- TDD order: test → red → implement → green (100% coverage required for all src/features/**)
- **Guard-suppression pattern** (WU-02-T4): any screen where an async call (`signUp`, `signInWith*`) creates a session as a side effect, followed by further async work before the screen navigates, must call `sessionCtx.setSuppressGuardRedirect(true)` before that call and clear it **only via a `useEffect` cleanup fired on unmount** — never in a `finally` block (that only narrows the race window, doesn't close it, since it can fire in the same render commit as an error becoming visible).
- **Retry-after-partial-success pattern** (WU-02-T4): when a flow has two sequential server calls and the first can succeed while the second fails independently, track completion of the first with explicit state (e.g. `accountCreated`) so a retry only repeats the failed step, not the whole flow.
- **Review packet structure** (updated 2026-07-02): lean, focused excerpts over full-document dumps; every packet needs "Dependency Call Chains" (nearest callers/callees/providers/guards/RPCs) and "Runtime Boundary And Mock Audit" sections; reviewer verdicts must include "Runtime Boundary Check". Self-enforced via `.beads/hooks/pre-commit`.
- **Synchronous re-entrancy guard pattern** (WU-02-T5): a `state` check alone (`if (submitting) return`) does NOT stop two synchronous event handlers dispatched before the first state update commits — both closures read the same stale value. Use a `useRef` mutated immediately instead (see `DeleteAccountModal.tsx`'s `submittingRef`).
- **Codebase-invariant source-scan test pattern** (WU-02-T6): for contracts that can't be unit-tested through mocks alone (e.g. "no client code ever calls X"), a jest test can walk `app/src` with real `fs`/`path` at test time and regex-scan file contents — a legitimate "presence check, not exhaustive" test type distinct from the project's usual mock-based behavioral tests. See `profileTrigger.test.ts`.
