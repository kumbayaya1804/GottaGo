## Findings

### 1. MAJOR — The Probity configuration has the wrong shape, so the declared `app/src/**` scope is not enforced

`probity.config.ts:8-9` puts `files` at the top level and places `enforceTdd()` directly in the top-level `rules` array. In Probity 1.10.0, `Config` contains a `rules` array of rule blocks; `files` belongs inside a block whose nested `rules` contains `enforceTdd()`. The installed package's own declarations reject the queued file:

`probity.config.ts(8,3): error TS2353: Object literal may only specify known properties, and 'files' does not exist in type 'Config'.`

This is not merely a type-only defect. The installed resolver treats a function directly in `Config.rules` as a global rule, so the current `enforceTdd()` applies to every matched write rather than only `app/src/**`. That contradicts `probity.config.ts:3-6`, `CLAUDE.md:57`, `docs/agent-harness.md:203`, and the packet's stated boundary.

Required fix: use a nested rule block, for example `rules: [{ files: ['app/src/**'], rules: [enforceTdd()] }]`, and add a typecheck or behavioral regression proving an in-scope path is enforced while an out-of-scope path is not.

### 2. MAJOR — The active root Probity policy file is outside the review-required path gate

`.claude/hooks/check-review-artifacts.js:35-46` protects selected root documents and `.claude/...` subtrees, but it does not protect the actual `probity.config.ts` file. The new test case at `.claude/hooks/check-review-artifacts.test.js:258` checks a hypothetical `.claude/probity/data/instructions.md`, not the queued root configuration.

Executing the shipped predicate produced `probity.config.ts => false`, while both `.claude/probity/data/instructions.md` and the retained inert `.claude/tdd-guard/data/instructions.md` pattern returned `true`. A future change can therefore weaken or remove the real TDD policy without being placed in the review queue, defeating check B's stated purpose.

Required fix: add an exact root-path rule such as `/^probity\.config\.ts$/` and a regression test using `probity.config.ts` itself. Keeping the inert TDD Guard path is harmless, but it does not address this omission.

### 3. MAJOR — The migration deletes project-specific enforcement instructions without translating them to Probity

The staged deletion of `.claude/tdd-guard/data/instructions.md:3-19` removes explicit checks for GPS/PostGIS distance logic, trust-score delta sign, RLS-denied paths, strict RED-GREEN ordering, and 100% coverage. The replacement at `probity.config.ts:9` invokes bare `enforceTdd()` defaults and supplies none of those project rules.

Probity 1.10.0 exposes an `instructions` option on `enforceTdd`, so there is a supported migration path. Deleting the only custom instruction source while claiming a tool migration materially weakens the prior project-specific policy even though generic TDD enforcement remains.

Required fix: preserve the project rules in a review-protected source and pass them through Probity's `instructions` option (or an equivalently enforced rule), with a regression proving the effective instruction set is loaded. If retiring those controls is intentional, make that policy change explicit and justify it rather than presenting it as a behavior-preserving migration.
