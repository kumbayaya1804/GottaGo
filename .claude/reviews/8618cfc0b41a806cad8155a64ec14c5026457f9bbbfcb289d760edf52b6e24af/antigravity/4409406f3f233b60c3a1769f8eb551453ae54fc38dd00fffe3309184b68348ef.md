### Concerns
- Claude Code Hook Dispatch on Windows without Git Bash: `.claude/settings.json` wires hooks as `node "$CLAUDE_PROJECT_DIR/.claude/hooks/harness-hooks.js" <command>`. On POSIX hosts (macOS/Linux), `/bin/sh` or `/bin/bash` expands `$CLAUDE_PROJECT_DIR`. On Windows hosts where Git Bash is present, Claude Code defaults to bash and expands `$CLAUDE_PROJECT_DIR`. However, if Windows invokes `cmd.exe`, bare POSIX `$VAR` syntax is not expanded by `cmd.exe` unless Claude Code pre-interpolates `${CLAUDE_PROJECT_DIR}`. The `harness-portability` CI matrix job added in `.github/workflows/ci.yml` will test `windows-latest` under GitHub Actions, but execution of Claude Code itself on Windows remains an unverified platform boundary.

### Adversarial Disproof
- **Premise 1**: Does `toRepoRelative` reject all paths that escape the repository via `..`?
  - **Counterexample attempted**: Invoked `toRepoRelative("a/../../outside.txt", "/repo")`.
  - **Outcome**: Disproved. `toRepoRelative` returned `"a/../../outside.txt"` because relative paths were not normalized with `path.posix.normalize()` before checking `startsWith('../')`. While downstream git execution (`git add -A -- <path>`) and the review gate fail closed, the function premise itself is disproved.
- **Premise 2**: Can a queued file starting with `-` or containing shell metacharacters cause option or command injection during `stage-queue`?
  - **Counterexample attempted**: Tested `stageQueue` with `--weird; echo PWNED $(whoami).txt`.
  - **Outcome**: Retained. Arguments are passed as an array after `--` with `shell: false` (`spawnSync('git', ['add', '-A', '--', ...paths])`), preventing option parsing and shell interpretation.
- **Premise 3**: Can `queue-edit` fail silently on invalid tool input and allow unreviewed code into master?
  - **Counterexample attempted**: Traced invalid JSON payload handling and gate behavior.
  - **Outcome**: Retained. `queue-edit` exits with status 1 on JSON parse errors. If an edit remains unqueued, Check B in `check-review-artifacts.js` fails closed at pre-commit because any staged protected file not present in `.claude/review-queue.txt` blocks the commit.
- **Premise 4**: Does `resolveProjectRoot` accidentally anchor to `app/.claude/` when invoked from `app/`?
  - **Counterexample attempted**: Ran resolution from nested subdirectory inside git repository with nested `.claude/settings.json`.
  - **Outcome**: Retained. `git rev-parse --show-toplevel` takes precedence over directory walk, correctly resolving the repository root.

- **Caller -> Shell -> Node -> Subprocess Boundary**: Claude Code invokes hooks through its configured shell. Replacing PowerShell one-liners with `node "$CLAUDE_PROJECT_DIR/.claude/hooks/harness-hooks.js" <command>` establishes a uniform Node runtime on POSIX hosts.
- **PostToolUse Hook Semantic Limits**: As confirmed by official documentation, `PostToolUse` executes after the tool has written to disk. If `queue-edit` fails, the edit is on disk but unqueued. The crucial defense-in-depth boundary is `check-review-artifacts.js` Check B and `.beads/hooks/pre-commit`, which check the staged index against the queue at commit time, failing closed if any protected file was modified without entering the review queue.
- **Subprocess Isolation in `run-isolated-db-suite.js`**: `makeRunSupabase` and `run-isolated-db-suite.test.js` both branch on `entry.toLowerCase().endsWith('.js')`, invoking `process.execPath` directly for npm shims and executing native binaries directly with `shell: false`, eliminating shell metacharacter expansion vulnerabilities.
