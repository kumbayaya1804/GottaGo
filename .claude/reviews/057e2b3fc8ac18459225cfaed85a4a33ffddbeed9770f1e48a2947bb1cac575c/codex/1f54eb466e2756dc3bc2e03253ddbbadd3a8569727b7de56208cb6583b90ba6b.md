### Findings

1. **MAJOR — successful verification can manufacture a false empty discovery result.** `useVerify.ts:29-35` removes the accepted row, then invalidates the candidate query even though it requests `refetchType: 'none'`. An invalidated query refetches when `/verify` remounts, despite the ten-second `staleTime` in `useVerifyCandidates.ts:65-70`. If the user taps Done and opens Verify nearby again within the discovery cooldown, `search_pending_submissions_nearby` advances `last_discovery_at` and returns zero rows (`supabase/migrations/20260717120100_phase5_discovery_rpc.sql:58-103`); `verify.tsx:290-295` then says “Nothing to verify nearby” although other candidates may exist. The same false empty answer can follow an immediate manual Retry after a failed response (`verify.tsx:265-285`) because the database may already have committed the cooldown claim. Preserve the locally filtered list until a safe refresh time and make Retry cooldown aware. Cover both sequences with tests that model the server's cooldown, not an RPC mock that always returns rows.

2. **MAJOR — the selected candidate survives a direct account change.** `verify.tsx:116-124` passes a new `userId` to the same `VerifyFlow` component without remounting or resetting `selected`. While the user-scoped query changes, `verify.tsx:184-188` continues to display the previous account's selected pending bathroom and can submit it under the new session. The existing account-switch test in `verifyLocation.test.ts:168-193` checks only query data, not this local state. Key the flow by user ID or clear the selection on user change, and test an account replacement while a row is selected. This is a cross-account state leak even though the server remains authoritative for accepting a verification.

3. **MAJOR — Android does not announce two important asynchronous states.** The empty-result view at `verify.tsx:290-295` and accepted view at `verify.tsx:409-433` have no `accessibilityLiveRegion`; `useIosAnnouncement` explicitly runs only on iOS (`verify.tsx:84-90`). Both states appear without a focus change, so TalkBack users can remain on the prior control without hearing “Nothing to verify nearby” or “Verified!”. Add Android live regions for these messages and check them on a device; the current tests mock React Native accessibility behavior.

4. **MINOR — a queued design reference still names the old verification RPC.** `docs/design/design-system.md:427` describes ERR-09 as coming from `submit_verification_event`, while the staged wrapper calls `verify_location` (`app/src/features/verify/verifyLocation.ts:25`). The same row places ERR-09 below “I'm Here”, but the implementation renders it above that button (`verify.tsx:537-589`). These differences are absent from the deviations table in `05-03-SUMMARY.md:93-103`, contrary to packet claim C10. Update the reference or document the deviation.
