### Findings

- [MAJOR] `.claude/hooks/check-review-artifacts.js:558-565`, `.claude/hooks/check-review-artifacts.test.js:507-528`, `docs/agent-harness.md:218-229` - The replacement detector still permits valid, single-line executions of the full gate, so the stated blind-review protection and the new disclosure are incomplete. Direct calls to the exported production helper returned `false` for all of these:

  - `node -r fs .claude/hooks/check-review-artifacts.js`
  - `node --inspect=0 .claude/hooks/check-review-artifacts.js`
  - `sh -c 'node "$0"' .claude/hooks/check-review-artifacts.js`

  These are executable shapes, not inert mentions. Harmless probes substituting `harness-hooks.js __probe__` reached that script in all three cases; Node's current CLI grammar expressly permits options before the program entry point, including options with attached or separate values. The regex accepts only repeated flag tokens matching `-{1,2}[\w-]+` immediately before the gate path. It therefore loses the path after a value-taking option (`-r fs`), rejects the option token at `=` (`--inspect=0`), and cannot associate a shell positional argument with `$0`. The passing test covers only a valueless option (`--no-warnings`) and a wrapper whose command string contains the literal path.

  Impact: a generated packet can accidentally tell a blind reviewer to run the full cross-review gate, the packet validator accepts it, and the command reads both canonical verdicts before the reviewer has archived an independent result. This is the approval-integrity failure the new guard is intended to prevent. `docs/agent-harness.md:221-224` also overstates the implementation by saying runtime/shell words may be followed by flags and that flag-prefixed spellings are caught, without limiting that claim to valueless flags. Calling the scanner a heuristic does not make those specific claims true, and the paragraph explicitly says the risk is not yet user-accepted.

  Required fix: make the command-shape analysis recognize at least Node options with attached values, Node options with a following value, and shell positional wrappers before the gate path; add each reproduction above to the real-gate integration test and add direct helper-level assertions so failures identify the parser rather than spending a full fixture run. Then narrow the documentation to the exact supported grammar. If the team instead wants these single-line forms outside the model, that is a governance decision requiring an explicit user-accepted risk statement; it cannot be approved as the present claim that single-line flag/wrapper forms are blocked.
