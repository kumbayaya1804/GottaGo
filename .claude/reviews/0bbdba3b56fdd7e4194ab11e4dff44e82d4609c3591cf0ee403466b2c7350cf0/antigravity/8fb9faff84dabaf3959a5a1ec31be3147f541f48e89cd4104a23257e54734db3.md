### Follow-ups
- NOTE (follow-up): Client and server disagree slightly on what counts as whitespace. I probed this on local PG 17.6:
  - Server `[:space:]` matches U+0085 (NEL). JS `String.prototype.trim` does not strip it. A name made only of NEL passes the wizard but gets the generic server error. No honest keyboard input produces this, so the friction is negligible.
  - Server `[:space:]` does not match U+FEFF (BOM), U+200B (zero-width space) or U+180E. JS trim strips U+FEFF. So a hostile client can stage invisible names (U+200B or BOM only). This does not threaten integrity, because `locations.name` stays non-NULL.
- NOTE (follow-up): The server does not cap `p_name` length. `submissions.name` has no CHECK, per the `pg_constraint` read. The 120-character cap exists only in the client, so a hostile authenticated client can stage an arbitrarily long name. This was already true before this batch and the change does not depend on it.

### Adversarial Disproof

- Ordering in submit_location. The name check comes before the GPS checks, so a request with a blank name and NULL coordinates raises `invalid submission`. Both messages are generic, so nothing leaks.
- Second-overload risk. `create or replace` with an identical identity signature: the catalog shows exactly 2 functions.
