### Findings
1. **User failure state: valid form progression can end in an unrecoverable retry loop.** The new `submit_location` name guard rejects spaces-only input with `invalid submission` (`supabase/migrations/20261016000000_phase5_rpc_input_validation.sql:447-449`). The shipped form accepts that input because `z.string().min(1)` checks length (`app/src/features/submit/submitSchema.ts:19`), then sends the unchanged name (`app/src/app/(tabs)/submit.tsx:223-227`). The RPC error is rethrown (`app/src/features/submit/submitLocation.ts:42-43`), while the screen says “Check your connection and try again” and Retry resends the same input (`app/src/app/(tabs)/submit.tsx:594-605`). This directly contradicts the packet's honest-path/no-new-friction claim and fails the 60-second user gate. Align the form's name validation with the server rule or give a recoverable name-specific path without exposing GPS rejection details; test that path.
2. **The new pgTAP suite does not prove caller-role behavior for either recreated `SECURITY DEFINER` RPC.** `pg_temp.act_as` changes only `request.jwt.claims` (`supabase/tests/phase5_rpc_input_validation.test.sql:34-39`); all RPC assertions run as the pgTAP `postgres` connection (`:42-122`). `postgres` bypasses the execute ACL and RLS. Existing `phase4_submit.test.sql` and `phase5_verify_publish.test.sql` likewise do not call these two RPCs under both actual `anon` and `authenticated` SQL roles. The project pgTAP and RLS skills require caller-role checks for changed RPCs. Add role-switched allowed and denied calls, including the new validation paths, before treating the unchanged grant text as runtime-proven.
