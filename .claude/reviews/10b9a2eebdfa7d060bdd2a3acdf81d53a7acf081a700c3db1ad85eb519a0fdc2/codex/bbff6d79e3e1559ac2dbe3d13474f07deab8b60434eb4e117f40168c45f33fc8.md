### Findings

#### 1. MAJOR - The claimed verbatim policy port still omits the original TDD Order rule and has no effective-config regression

`probity.config.ts:17-20` says the deleted TDD Guard project rules are preserved “verbatim” and “not silently retired,” but the actual addendum at `probity.config.ts:22-51` omits `.claude/tdd-guard/data/instructions.md:15-16` in full: the `## TDD Order` heading and its rule requiring a failing test to be written and observed before implementation. The migration also changes the top heading and reformats the retained prose, so the packet's claimed direct/verbatim comparison cannot have succeeded as stated. Direct extraction measured 1,329 characters in the deleted source versus 1,127 in the addendum and reported `TDD Order old=true addendum=false`.

The installed Probity 1.10.0 defaults currently cover the core Red-to-Green semantics, and the corrected `app/src/**` block scopes those defaults correctly, so this is not the same immediate fail-open behavior as round 1. It is still an unresolved migration-contract defect: the queued source and packet make a false preservation claim, and no test loads the real config and asserts that both default TDD ordering and every project-specific section reach the effective validator prompt. A later Probity-default change could therefore remove the relied-on replacement without any repository regression failing.

Required fix: either restore the missing `TDD Order` section and make the addendum genuinely complete, or explicitly document that this one rule is intentionally supplied by Probity's defaults rather than ported verbatim. In either case, add a focused regression that loads `probity.config.ts` through Probity's real `loadConfig()`/engine path, proves an `app/src/**` write invokes the rule while an out-of-scope write does not, and asserts the captured effective prompt contains the default test-first rule plus all intended project-policy sections.
