### Findings
- **[MAJOR] `supabase/migrations/20260731000300_phase5_verify_and_publish.sql:154-165` — the first-use verification cooldown has a missing-row concurrency bypass.** Step 2 executes `SELECT ... FOR UPDATE` before ensuring the caller's `private.verification_rate_limits` row exists. For a new caller, the SELECT returns no row and locks nothing. Two concurrent first-ever calls can therefore both read `v_last_attempt = NULL`, reach the upsert, and both continue after serialization without re-reading the winner's timestamp. I reproduced this in a disposable database with two dblink sessions deliberately held at the first INSERT boundary: both sessions were observed waiting, then both returned `{"accepted": true}`; the pgTAP assertion expecting exactly one accepted call got 2. This violates the D-36 per-user cooldown and permits a fresh account to submit two verification events/trust effects inside one cooldown window. Required fix: establish the per-user row first (for example, `INSERT ... VALUES (v_uid, NULL) ON CONFLICT DO NOTHING`), then lock and read that existing row, then update its timestamp and decide from the locked previous value, matching the atomic discovery-cooldown pattern. Add a deterministic two-session regression covering two simultaneous first-ever `verify_location` calls by one user against different pending submissions; require exactly one accepted call and one reason-free cooldown rejection.
