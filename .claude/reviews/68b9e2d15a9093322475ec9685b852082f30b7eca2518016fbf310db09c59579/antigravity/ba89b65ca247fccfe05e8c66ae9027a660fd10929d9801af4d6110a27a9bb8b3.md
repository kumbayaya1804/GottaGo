### Adversarial Disproof
- **Premise 1**: Could `insert ... on conflict (user_id) do nothing` followed by CTE `select ... for update` allow a race condition if two calls for a new user execute concurrently?
  - **Counterexample attempted**: Analyzed PostgreSQL locking behavior for `insert ... on conflict do nothing` and CTE `for update`.
  - **Outcome**: Disproved. The INSERT ensures the row exists. The CTE `select ... for update` acquires a row-level `FOR UPDATE` lock on `private.verification_rate_limits(user_id = v_uid)`. Any concurrent call by the same user MUST wait on that row lock until the first transaction commits/rolls back. Upon acquiring the lock, the second transaction reads the first's updated `last_verify_attempt_at` timestamp and evaluates `(v_now - v_last_attempt) < make_interval(secs => v_cooldown_s)`, returning `accepted: false`.
- **Premise 2**: Does `v_now` (frozen transaction timestamp) present a vulnerability compared to `clock_timestamp()`?
  - **Counterexample attempted**: Evaluated single-transaction behavior and pgTAP fixture compatibility.
  - **Outcome**: Verified. In `verify_location`, all validation and state modifications occur in a single atomic transaction. `v_now` is consistent across all steps in the function, ensuring deterministic evaluations without drift within a single call.
